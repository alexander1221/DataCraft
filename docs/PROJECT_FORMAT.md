# Проекты и черновые графы

## §1. Задача

Проект должен сохранять промежуточное состояние редактирования. Отсутствующий
вход или пустой параметр — диагностика черновика, а не повреждение файла.
При этом UUID, рёбра, типы конфигураций и DAG должны оставаться корректными.
Формат JSON .dcraft остаётся версии 1, новых постоянных полей не добавляется.

Новые варианты config.kind описаны в [NODES.md](NODES.md). Split сохраняет
key_columns, train_fraction и seed; edge.from_port указывает train или test.
Fit-ноды сохраняют параметры, но не обученные модели. Model передаётся только
внутри одного job; новый запуск повторяет fit. Позиции и параметры сохраняются
как прежде. Пути CSV/Parquet/JSON разрешаются относительно файла проекта;
Save as сохраняет их назначение, в том числе в undo/redo history.
Старые v1 fixtures продолжают загружаться; старое приложение может отклонить
новый kind, поэтому совместимость новых нод с прежним бинарником не обещается.

## §2. Алгоритм

Загрузка/сохранение проверяют версию, имя проекта, целостность графа и designated
output. Полная валидация дополнительно требует корректных параметров и всех
входов. Запуск проверяет целостность всего проекта, затем готовность только
выбранного выхода и его предков. Проверка схем и SQL выполняется в Spark.

## §3. Применения

Сохранить новую неподключённую ноду; открыть черновик и получить диагностику;
выполнить готовую ветку рядом с незавершённой. При запуске незавершённого
выхода ошибка возвращается до создания JVM. Открытие/сохранение не запускают
вычисления и не проверяют существование источников данных.

## §4. Контракты

Project: format_version=1, name (непустая строка), nodes, edges,
optional output_node. Node: UUID id, position=[x,y], typed config с kind.
Edge: from/from_port/to/to_port. Поля параметров обязательны согласно типу
NodeKind; черновик содержит пустые/неподходящие значения, а не пропущенные поля.

Жёсткие ошибки: неизвестная версия/kind, неверные типы JSON, повторный UUID,
несуществующая нода/порт, несовместимые типы, повторное соединение single-input,
цикл, нечисловые/бесконечные координаты/float-параметры, неверный output_node.
Они запрещают load/save/run, даже если находятся в неиспользуемой ветке.

Диагностика черновика: нарушение параметров NodeSpec и отсутствующие входы.
Graph::diagnostics возвращает все такие проблемы в порядке UUID; сначала
параметры ноды (первая ошибка), затем входы в порядке NodeSpec. Сами параметры
не исправляются. Проверка целостности предшествует сбору диагностики.

Graph::validate сохраняет строгую семантику; validate_structure разрешает
неполный граф. Project::validate также остаётся строгим; load/save/to_json/
resolved используют validate_structure. output_node может отсутствовать или
указывать на незавершённый, но существующий selectable output.

NodeSpec::create_draft_config применяет defaults, а обязательные поля без
defaults заполняет типизированными placeholders: строка "", список [], bool
false, integer 0, float 0. create_config остаётся строгим.

CLI validate без флага требует готовности всего графа; validate --draft проверяет
целостность и печатает диагностику, возвращая 0 для допустимого черновика.
run использует --output, затем output_node, затем единственный выход; неоднозначность
не устраняется автоматическим выбором «готового» выхода.

## §5. Реализация

crates/datacraft-core: Graph, GraphDiagnostic и NodeSpec factory;
crates/datacraft-project: Project persistence; engine/CLI: preflight запуска.
Пример examples/pipelines/draft.dcraft содержит рабочую sample-ветку и
неподключённый Filter с пустым expression.

## §6. Замечания

JSON-сериализация не должна молча заменять NaN/Inf на null: такие значения
отклоняются до записи. Пустые и нелокальные source paths черновика не преобразуются
при resolved; для готовой ветки их отклонит валидация параметров. Валидные пути
разрешаются относительно файла проекта, persistent-копия не меняется.
Сохранение сохраняет существующую atomic-tempfile политику и защиту версий.

## §7. Приёмка

Тесты: round-trip черновика с placeholders, сохранение/повторная запись,
неповреждение файла при невалидном save, полные детерминированные diagnostics,
готовая ветка среди незавершённых, отказ запуска неполной ветки,
отказ структурно повреждённого графа. Прежние fixtures остаются совместимыми.
Результаты: 33 Rust-теста, fmt/check/Clippy, диагностика черновика и четыре
реальных CLI/Spark-запуска прошли на Windows. Подробности, исходный неуспешный
прогон и ограничения проверки находятся в docs/VALIDATION.md.

## §8′. Устойчивость

Структурная корректность не означает возможность выполнить pipeline: файл может
не существовать, SQL/схема — не подходить. Топологическая проверка глобальна;
цикл в неиспользуемой ветке не становится допустимым. Не производится скрытый
ремонт рёбер, сброс параметров или смена версии. Пустой проект допустим для
сохранения, но не имеет исполняемого выхода.
