# Выполнение на canvas

## §1. Задача

Показывать состояние выполнения каждой ноды по событиям worker. Состояния
относятся к снимку проекта и не сохраняются в `.dcraft`.

## §2. Алгоритм

Worker сообщает начало обработки ноды и подготовку её плана. Успешный ответ
подтверждает выполнение выбранной ветки. Подготовленный ленивый DataFrame
сам по себе не подтверждает успешного чтения всех строк. Ошибка относится
к ноде, на которой worker её обнаружил; это может быть downstream action.

## §3. Применение

Зелёный контур обозначает успешное выполнение, красный — ошибку.
Заливка ноды остаётся обычной тёмной независимо от статуса.
Колесико справа сверху показывает текущую обработку. Отмена и timeout
не должны превращаться в успешное выполнение. Перемещение нод сохраняет
индикацию, изменение вычислений делает её неактуальной.

## §4. Контракт

UUID ноды стабилен. Новые progress frames включаются запросом клиента,
содержат protocol_version, request_id, node и фазу. Итоговый ответ сохраняет
существующий формат. Каждая строка ограничена 8 MiB. Статусы не зависят
от графических объектов. Длительная работа выполняется вне UI thread.

▶ выполняет строго выбранную ноду, ⏩ — её и всех потомков в топологическом
порядке. Родители вне выбранного множества должны иметь актуальные результаты.
При отсутствии входа запрос отклоняется до запуска. Worker живёт до закрытия
проекта; модели и MEMORY_AND_DISK таблицы остаются только на время сессии.
Таблица материализуется через persist + count, без collect полного набора.
Split материализует оба выхода. Просмотр ограничен 1000 строками и 8 MiB.
Изменение config/входящих рёбер сбрасывает ноду и потомков; движение, имя
проекта и изменение designated output не сбрасывают кэш. Явный повторный
запуск ноды также сбрасывает её потомков, чтобы обновить изменившиеся файлы.
Отмена/timeout/сбой JVM сбрасывают весь кэш. Обычный Run project сохраняет
ленивое выполнение; он не заполняет поузловой кэш.

## §5. Реализация

`Session` принимает `execution.node.run` / `execution.downstream.run` с UUID
в `node_id`. Команды возвращают JobStarted и используют общий JobManager,
cancel/timeout и polling. `Session::node_statuses()` возвращает снимок статусов.
`node_runtime.rs` сопоставляет config, входящие рёбра и токены родителей.
События старого снимка не обновляют изменённые ноды. Scala `Worker.Cache`
хранит таблицы по `(UUID, port)` и модели по UUID. При следующем запросе
несовпадающие токены освобождаются через unpersist. Временные файлы управляются Spark.

## §6. Замечания

Кэш не является гарантированным checkpoint: Spark может пересчитать потерянные
разделы по lineage. Строгость относится к выбранным DAG-операциям DataCraft,
а не к запрету внутреннего Spark recomputation. Внешние изменения файлов
автоматически не отслеживаются: для обновления нужно запустить Source заново.
Материализация всех промежуточных таблиц требует времени и места на диске.
Память операторов и размер отдельной ячейки не ограничиваются preview limit.
Обычный Run использует отдельную JVM; постоянный worker с кэшем может в это
время оставаться в памяти. Межсессионный Parquet/checkpoint пока отсутствует.

`Done (cached)` означает материализованный результат. `Done (pipeline)` —
успешное завершение использующей ноду ленивой ветки, а не чтение всех строк
каждой промежуточной таблицы. При отмене/ошибке процесса готовые входы теряются.
Завершённые до обычной query-ошибки ноды в постоянном worker остаются готовыми.

## §7. Приёмка

```text
cargo run -p datacraft-engine --example node_lifecycle
cargo test -p datacraft-desktop --features spark-integration-tests node_run_button -- --test-threads=1
```

Независимые ожидания: sample возвращает quantity 4, 5, 6; запуск Filter без
Source отвергается без JVM; движение не меняет готовность; изменение Filter
сбрасывает только его и потомков. Scala NodeExecutionSuite удаляет временный
CSV после материализации и проверяет последующую обработку из кэша; отдельно
проверяет fitted Model, ветвящийся граф и оба выхода Split.
Фактические результаты и границы платформ: [VALIDATION.md](VALIDATION.md).

## §8′. Устойчивость

Протокол проверяет version/request UUID, принадлежность ноды выбранному scope,
порядок running → prepared/completed и обязательные completion frames для
поузлового режима. Число frames ограничено `2 * nodes + 1`, размер строки —
8 MiB. Общий preview response также ограничен; ошибка не выдаётся за успех.
Переполненная очередь событий не теряет статусы: authoritative map хранится
отдельно. Сбой JVM обнаруживается при следующем запросе; до этого canvas
не является heartbeat. Закрытие/смена проекта посылает EOF и best-effort kill
idle worker; ожидание reaping вынесено с UI thread. При аварийном завершении
host подтверждённая очистка временных файлов не гарантируется.
