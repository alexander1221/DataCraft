# Ворота сдачи DataCraft

## G1. Независимый оракул

Для DAG — сформулированные инварианты; для JSON — контракт версии/схемы;
для ML — аналитическое решение или независимый эталон; для внешней команды —
настоящий вывод с версией и датой. Snapshot собственного вывода не доказывает
правильность. Фикстуры содержат происхождение и допустимые преобразования.

## G2. Независимая приёмка

Для изменений с высоким риском потери данных, ошибочной статистики или
нарушения границ процессов нужен независимый reviewer: человек или отдельно
авторизованный агент. Дайте ему контракт §1–§4 без реализации и ожидаемого ответа.
Расхождения классифицируйте как дефект кода, контракта либо теста. Если проверка
недоступна, отметьте отсутствие; не изображайте собственный второй просмотр
независимым review и не расширяйте права ради проверки.

## G3. Свойства и сценарии

Проверяйте round-trip, canonical serialization, порядок DAG, типы портов,
ошибки версий, schema preservation и bounded previews. Проверяйте повторный
запрос после ошибки. Каждому обещанному применению соответствует приёмочный
сценарий; smoke test не заменяет проверку корректности чисел.

## G4. Внешние зависимости

Проверьте официальные API/версии и actual dependency resolution. Команды
cargo metadata/cargo tree и sbt update/show scalaVersion/show dependencyClasspath
дают разные свидетельства; выполняйте в нужном проекте и записывайте результат.
Отсутствие сети и package-not-found — разные исходы. Нельзя выдавать Python
wheel-checker за Maven/Cargo compatibility check.

## G5. Реальный потребитель

Соберите и исполните CLI с настоящим worker на Windows, Linux и macOS прежде,
чем объявить платформы поддержанными. В релизной приёмке используйте чистое
окружение и команды README: пути из другой CWD, Unicode paths, отсутствующий
worker/JDK, nonzero exit codes и ошибки данных. PowerShell 5.1 проверяется
отдельно от pwsh. GUI проверяется настоящим приложением.

## G6. Реестр утверждений

Записывайте источник, дату и конкретную границу verified; неизвестное —
ASSUMPTION с планом проверки. Различайте PASS, FAIL и NOT_RUN. Обновляйте
реестр после изменения зависимостей, не только первый упавший URL.

## G7. Прицельные мутации

Для критичных парсеров/валидации/чисел используйте направленные дефекты:
пропуск version check, снятие preview limit, перепутанный label, слабый допуск.
Проверяйте, что тест обнаруживает дефект. Не вводите произвольный процент
убитых мутантов; классифицируйте выжившие. Не подключайте тяжёлый mutation
tool для каждой небольшой правки без пользы.

## G8. Статика и сборка

Rust: cargo fmt --all -- --check; cargo check --workspace;
cargo test --workspace; cargo clippy --workspace --all-targets -- -D warnings.
Scala worker: sbt test writeClasspath из workers/spark. После появления
Cargo.lock добавьте --locked там, где команда поддерживает.
Изменения только навыка не требуют новой сборки приложения: валидируйте
инструкции, references и добавленные helper scripts.

scripts/validate_generated.py выполняет дешёвую проверку артефактов; он не
заменяет эти команды и не обещает сетевой аудит. AST Python не означает
импорт/исполнение; TOML parsing не означает cargo check.

## G9. Проверка границ

Просматривайте filesystem writes, перезапись проектов, process arguments,
кодировки/framing, лимиты памяти и ошибок, lifecycle JVM, обработку unsupported
format и пути данных. Это отдельная работа от метрик покрытия. Не скрывайте
stderr; возвращайте ошибку с полезным контекстом.

## Итоговый отчёт

Кратко укажите изменения, выполненные проверки, непройденные/неисполненные
проверки и открытые ASSUMPTION. Отсутствие окружения не мешает сдать reviewable
результат, но запрещает объявлять его собранным, работающим или эквивалентным
без свидетельств.
